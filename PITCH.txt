DOODLE ARENA (Doodle FFA): PITCH NOTES
======================================
MHacks 2026


1. SUMMARY
----------
- What it is: a same-room party battle royale for 2-12 players. Everyone uses their phone as the
  controller, and the fight plays out on one shared big screen (TV / projector / laptop).
- The hook: you DRAW your weapon. Any doodle (a sword, a squiggle, a flower) becomes a real,
  working, balanced weapon with its own attack style, sound and art.
- One round, about 3 minutes:
    - Draw (20 s): sketch a weapon on your phone.
    - Drop: you get a random special ability, then pick where you land in the arena.
    - Reveal: the big screen shows off every weapon, with a 3-2-1 countdown. Each weapon gets an
      "upgrade" moment where the doodle turns into finished art, and a commentator reads its name.
    - Battle (60 s): joystick plus attack button on your phone. A storm shrinks the arena, with
      sudden death at the end.
    - Results: top-3 podium, then play again.
- Multiplayer only: everyone plays on their own phone (at least 2 players).
- Our core idea is the "invisible middle". AI turns your doodle into a weapon, but players never
  see "AI", "generating", spinners or stats. It just feels like magic: draw it, and it works.
- Fair by design: however wild the drawing, a server-side balance formula evens out damage per
  second, so a good doodle is about creativity, not about breaking the game.
- A round never stalls: every AI step has an instant fallback, so if a service is slow or down,
  the game keeps going.


2. TECH STACK
-------------

2.1 Overview: how the pieces fit together
- PERSONAL DEVICE (controllers): draw, pick abilities, move, attack.
- BIG SCREEN (shared display): renders the arena, the reveal, the scoreboard and the commentator.
- GAME SERVER (SpacetimeDB): the single source of truth. It holds all game state, runs the battle
  simulation 20 times a second, and is the only thing that calls the AI services.
- AI SERVICES (called only by the game server, never by browsers):
    - ASI:One (Fetch.ai): doodle -> weapon rules (JSON), plus commentary lines.
    - xAI Grok Imagine: doodle -> finished weapon art (image to image).
    - ElevenLabs: commentator voice, weapon-name announcements and weapon sound effects.
- HOSTING: the website (phone and screen pages) is a static site on AWS S3 + CloudFront at
  https://doodleffa.tech. The game server runs on SpacetimeDB Maincloud.
- Everything talks to the game server over one live WebSocket connection. Phones and the screen
  never talk to each other directly; they all subscribe to the same server tables, and updates
  stream to them automatically.

2.2 Monorepo and language
- One TypeScript codebase, managed with pnpm workspaces. There are 4 packages:
    - client/: the website (phone controller, big screen, title menu, dev tools).
    - server/: the SpacetimeDB game-server module.
    - packages/spec/: shared weapon "rules of the game".
    - packages/engine/: shared rendering and animation code.
- Why one language: the server, the phones and the screen all import the SAME weapon rules
  (packages/spec), so they can never disagree about what a weapon is or does.
- Tooling: Vite (dev server and build), Vitest (about 210 automated tests), tsx (scripts),
  Playwright (driving real browser rounds for end-to-end checks).

2.3 Client (website): Vite + PixiJS + three.js
- One web app with several pages:
    - /play: the phone controller. Drawing canvas, ability pick, drop spot, joystick, attack and
      special buttons, and your own weapon card.
    - /screen: the shared big screen. Lobby with QR code, tutorial loop, reveal show, arena,
      scoreboard, podium.
    - Title menu.
    - /dev/weapons: an internal lab for testing every weapon type and decoration.
- PixiJS v8 (2D): draws the doodles, weapons, projectiles, hit effects, screen shake and glow
  filters. The doodle is cut out of its white background so only the drawn lines show.
- three.js (3D): a rigged low-poly stick-figure character (from Mixamo) with a run cycle. Attack
  motions are layered on top in code, so one character can swing, thrust, slam, shoot and so on.
  A tilted overhead camera gives the arena depth.
- nipplejs: the on-screen joystick on phones.
- qrcode: the join QR code in the lobby.
- Phone polish: no pinch zoom, rotate-to-landscape hint, damage-only vibration (your phone buzzes
  only when another player hits you), and a "hear your weapon" button.
- Connection to the rest:
    - Uses auto-generated SpacetimeDB "bindings": typed TypeScript code that mirrors the server's
      tables and actions.
    - The client calls server actions (join room, submit drawing, move, attack) and subscribes to
      tables (room, players, fighters, weapons, effects), redrawing whenever rows change.
    - The screen smooths 20 Hz server updates into 60 fps motion (interpolation).

2.4 Game server: SpacetimeDB (TypeScript module)
- SpacetimeDB is a database that runs our game logic inside it. There's no separate backend
  server, API layer or cache; the database IS the server.
- Tables hold all state: rooms, players, drawings, weapons, fighters, inputs, projectiles,
  ability objects, visual-effect events, commentary, secrets.
- Reducers (fast, transactional actions): create/join room, start round, submit drawing, send
  input, press ability. Each one runs atomically, so there are no race conditions between 12 phones.
- A scheduled "tick" reducer runs the battle simulation 20 times a second: movement, attacks,
  hit detection, knockback, projectiles, abilities, storm, sudden death and eliminations.
- Procedures (slower actions that can make web requests): the only place AI services are called.
  This keeps API keys on the server, never in the browser.
    - gen_spec: doodle -> weapon rules (ASI:One).
    - gen_sprite: doodle -> weapon art (xAI).
    - gen_sfx: weapon sound (ElevenLabs).
    - gen_commentary and gen_announcement: commentator lines and speech (ASI:One + ElevenLabs).
- API keys live in a private `secrets` table that no client can read.
- Connection to the rest: clients subscribe with SQL-style queries (for example "my room's
  fighters"), and SpacetimeDB pushes only the changed rows to each device in real time.

2.5 Shared weapon rules: packages/spec
- A weapon is a small JSON "spec" built from fixed building blocks:
    - 8 archetypes (attack styles): swing, thrust, slam, shoot, throw, whip, spin, beam.
    - Projectile behaviors (pierce, bounce, split, homing, arc), decorations (flames, sparkles,
      gems...), a name, and a sound description.
- validate.ts: checks any AI output, clamps numbers into safe ranges and fixes or drops invalid
  fields. The AI can't invent anything the engine can't render.
- fallback.ts: builds a weapon from the drawing's shape alone (length, curviness, colors) with no
  AI at all. Seeded, so the same doodle always gives the same result.
- 20 special abilities (Flash, Dash, Smoke, Invisible, Nukes, Freeze, Hook, Life drain...).
  Cooldowns are capped at 22 s.
- Timing and arena-size rules shared by the server and screen. The arena grows with the number
  of players.
- Connection to the rest: the server uses it to validate and balance weapons; the client and
  engine use it to render and animate them identically.

2.6 Rendering engine: packages/engine
- Draws each archetype's attack motion and hitbox shape (an arc for swing, a line for thrust, a
  circle for slam, and so on).
- Decorations layer: adds the AI-chosen flames, sparkles and gems AROUND the player's original
  lines, with a "reveal" animation.
- Cutout: removes the white background from doodles and AI art.
- The 3D character, materials and camera projection shared by the arena, reveal and podium.

2.7 AI: ASI:One by Fetch.ai (text and vision LLM)
- `asi1` (vision model): looks at the doodle image and returns a weapon spec as strict JSON. A
  schema forces the exact shape, so we never parse free text.
- `asi1-mini` (fast text model): writes short, punchy commentator lines (KOs, final duel, winner).
- Weapon Smith uAgent (agents/weapon_smith/, Python): the same prompt and schema wrapped as a
  Fetch.ai agent. The game can use it as its weapon designer (SPEC_PROVIDER=agent): the game server
  calls the agent's authenticated REST endpoint, and the agent calls ASI:One and checks and
  balances the result with the game's own TypeScript rules. Live test: about 3.6 s per weapon.
- The same agent also takes text requests over Fetch.ai's chat protocol (ACP 0.3.0): "forge me an
  ice spear" returns a balanced weapon. Its contract is auto-exported from the TypeScript source
  so the two can't drift apart.
- Connection: the gen_spec procedure sends the PNG -> ASI:One returns JSON -> validate ->
  balance formula -> the weapon row is saved -> every screen and phone updates instantly.

2.8 AI: xAI Grok Imagine (image to image)
- `grok-imagine-image` takes the player's doodle and returns a finished, colored, cel-shaded
  version of THE SAME weapon. Silhouette, position and colors are kept, so it still feels like
  your drawing.
- Measured: about 8 s per image, about 100 KB JPEG at 1024x1024, about $0.02 per image.
- It starts the moment you submit your drawing, so it's ready by the Reveal "upgrade" moment.
- Connection: the gen_sprite procedure sends the PNG -> the art is stored inline in the weapon row
  (small enough that no separate file storage is needed) -> the screen cuts out the white
  background -> shown on the phone card, reveal, arena and podium. If it fails, the player's
  original doodle is used.

2.9 Audio: ElevenLabs
- Text-to-speech (`eleven_flash_v2_5`, voice "Adam"):
    - A sports-style commentator on the big screen, with white captions in the bottom-left corner
      so the room can follow along even when it's loud.
    - Reads each weapon's name during Reveal ("Maya's Thunder Noodle!").
    - Each phone announces "your weapon is ..." to its own player.
- Sound effects API: a one-second custom sound for each weapon, made from a sound description the
  AI writes for that weapon.
- Music: the title-menu loop was made ahead of time with ElevenLabs (a static file, no live cost).
- Connection: procedures call ElevenLabs -> the line's text and audio bytes come back to the
  screen/phone -> the audio plays in sync with the reveal timing while the caption shows.

2.10 Hosting: AWS + SpacetimeDB Maincloud
- Domain: doodleffa.tech (and www.doodleffa.tech). The QR code in the lobby links phones to
  https://doodleffa.tech/play?room=CODE.
- Website: a static build (HTML/JS/CSS) uploaded to Amazon S3, served worldwide through
  CloudFront (CDN + HTTPS). The setup:
    - S3 bucket: private (all public access blocked). Only CloudFront can read it, through Origin
      Access Control (OAC).
    - CloudFront: HTTP redirects to HTTPS. Missing paths (403/404) return index.html with a 200, so
      the website's own router handles /play, /screen and /dev/weapons.
    - HTTPS: a free AWS Certificate Manager (ACM) certificate for both names, checked through DNS.
    - DNS: a Route 53 hosted zone. A and AAAA (IPv6) alias records point the bare domain and www at
      CloudFront.
    - Caching: hashed JS/CSS files are cached for a year; index.html is always rechecked, so a
      new upload shows up right away.
- Game server: published to SpacetimeDB Maincloud (managed hosting).
- Why this split: the website is just files, so a CDN is the cheapest and fastest way to serve
  them. Everything live (state, simulation, AI calls) lives in SpacetimeDB.
- AI images don't need S3: they're small enough (about 100 KB) to travel through the game server.

2.11 End-to-end pipeline: one round, step by step
1. LOBBY: the big screen creates a room and shows a QR code. Phones scan it, join the room and get
   a locked player color. The screen loops a tutorial of the phone controls.
2. DRAW (20 s): each phone draws on a canvas. On submit, the phone sends the strokes, a PNG and
   shape "features" to the server, then fires the AI procedures in the background:
     - gen_sprite (xAI): doodle -> finished art.
     - gen_spec (ASI:One): doodle -> weapon JSON, then gen_sfx (ElevenLabs) -> weapon sound.
3. DROP: phones get a random special ability and pick a landing spot. This ends early once
   everyone has dropped. The AI keeps working meanwhile.
4. REVEAL: the server locks in every weapon. Anything the AI didn't finish gets an instant
   fallback (weapon built from the drawing's shape, original doodle art, stock sound). The screen
   shows each weapon with its "upgrade" moment while the commentator reads its name, then 3-2-1.
5. BATTLE (60 s): phones stream joystick and button input -> the server's 20 Hz tick simulates
   everything -> SpacetimeDB pushes fighter positions, HP and effect events -> the screen draws at
   60 fps, and the victim's phone vibrates on damage. The storm closes in, sudden death starts at
   50 s, and the commentator reacts to KOs.
6. RESULTS: top-3 podium with each player's weapon art. Drawings are cleared, and the next round
   can start.

2.12 Weapon generation workflow: drawing -> weapon, in detail
1. DRAW (phone):
   - The canvas records VECTOR strokes, not just pixels: each stroke has a color, a width and a
     list of points.
   - On submit, the phone sends 3 things to the server (the `submitDrawing` reducer):
       - the strokes (JSON),
       - a 512x512 PNG of the canvas,
       - shape "features" measured from the strokes (packages/spec/src/features.ts): stroke count,
         ink length, jaggedness, closed shapes, spiral score, symmetry, aspect ratio, coverage,
         colors used, and whether it's empty.
2. BACKGROUND AI CALLS (fired by the phone right after submit, each one switched by a flag in
   client/src/routes/play/draw.ts):
       - gen_sprite (RUN_SPRITE_GENERATION, ON): PNG -> xAI -> finished art -> weapon row.
       - gen_sfx (RUN_SFX_GENERATION, ON): ElevenLabs -> a custom weapon sound.
       - gen_spec (RUN_GENERATION, ON): PNG -> ASI:One -> weapon rules (JSON) -> validate ->
         weapon row. Takes about 3-5 s. gen_sfx then uses the AI's sound description.
3. SHAPE-BASED WEAPON (fallbackSpecFromFeatures, no AI): the backup if the AI is slow or fails.
   - Archetype from the shape:
       - spiral-like -> spin (if it has a closed shape) or throw;
       - long and thin -> whip (if jagged) or thrust;
       - covers a lot of the canvas -> slam;
       - many strokes -> shoot;
       - otherwise -> swing.
   - Effects from the main colors (for example red -> fire), plus electric for a jagged drawing.
   - Name: a seeded adjective plus an archetype noun (for example "Spicy Hammer"). Grip position
     comes from the aspect ratio.
   - Deterministic: the same doodle always gives the same weapon.
4. FREEZE (during Drop): when the player taps Next on the phone's weapon tutorial, the
   `prepareWeapon` reducer locks in the weapon, so the phone can teach "here's how your weapon
   works". If the AI is still designing, it waits for it (up to 8 s from the start of Drop) before
   using the shape-based backup. At Reveal, `applyFallbacks` fills in anyone who isn't locked in yet: a shape-based
   weapon, or "Mystery Stick" for an empty drawing.
5. BALANCE: `storeWeapon` runs the balance formula (same damage-per-second target, plus cooldown
   and knockback by type) and saves the weapon. Every screen and phone updates instantly.
6. RENDER: the screen draws the xAI art (or the doodle PNG cut out of its white background), the
   decorations, and the archetype's attack motion. The vector strokes are used to MEASURE the
   drawing, not to draw it.

4. DESIGN CHOICES
-----------------

Gameplay and experience
- The invisible middle: no "AI", "generating", spinners or stats in any player-facing screen.
  Prompts, raw AI output and debug info stay on the server (developer-only ?debug overlay).
- Open-ended but bounded: the AI picks from fixed building blocks (8 archetypes, projectile
  behaviors, decorations) and never writes code or free-form stats. Anything you draw works, and
  nothing can break the engine.
- Fair under the hood: the server balance formula targets the same damage per second (900) for
  every weapon. A huge slow hammer and a fast dagger are equally viable. The AI only picks flavor,
  never final numbers.
- Keep the player's drawing: the AI never replaces your doodle. Art keeps your silhouette and
  position, and decorations are added AROUND your lines. The game should feel like your creation.
- Short and juicy: about 3-minute rounds, 20 s to draw, 60 s to fight, with screen shake,
  knockback per weapon type, hit flashes, a commentator and a podium.
- 5000 HP scale: big damage numbers feel better than small ones, at the same balance.
- Locked player colors: each player keeps one color for the whole session, so friends can find
  themselves on screen instantly. Colors can't be changed.
- The arena scales with player count: more players get a bigger map. The storm starts outside the
  frame and shrinks in.
- Phones show only what matters: a big attack button, a joystick, a special-ability button, and
  vibration only when someone else hurts you (not for your own attacks or the storm).

Reliability ("a round never stalls")
- Every AI step has an instant fallback:
    - No weapon spec -> a weapon built deterministically from the drawing's shape.
    - Empty drawing -> "Mystery Stick".
    - No art -> the original doodle, cut out with an outline and glow.
    - No sound -> a stock sound for that weapon type.
- AI work starts the moment you submit and runs in the background during Drop, so it's usually
  done before Reveal. The game never waits on it.
- Each room's simulation is isolated, so one bad room can't crash the others.
- The screen keeps its room code across reloads, so phones never see "room not found".

Architecture
- One TypeScript codebase, so the server, phones and screen share the exact same weapon rules.
- SpacetimeDB as both database and game server: real-time sync is built in, and the simulation
  is authoritative on the server (no cheating from phones).
- AI calls only from the server: API keys never reach a browser, and all output is validated
  before any player sees it.
- Strict JSON schema for the LLM: the model must return the exact weapon shape.
- Provider-agnostic: validation, balance and fallbacks don't care which AI produced the JSON, which
  let us swap image providers (Gemini -> Bedrock -> xAI) in minutes.

Cost and usage (we planned around credits)
- SpacetimeDB: about 18,000 server calls for one full 12-player round. We develop on a free local
  server, so credits only burn on Maincloud. Before deploying, the always-running 20 Hz tick
  should pause when no room is active, or it burns about 1.7M calls a day while idle.
- ASI:One: about 1,500 tokens and about 2.5 s per weapon spec (`asi1`). Commentary lines
  (`asi1-mini`) take about 0.8 s.
- xAI: about $0.022 per weapon image, so the $25 credit covers about 1,100 weapons (about 90 full
  12-player rounds).
- ElevenLabs: about 6 commentator lines per round, capped at 16, with a minimum gap between lines.
  Weapon-name intros skip the LLM entirely (just "<player>'s <weapon>!").
- Static website on S3 + CloudFront: pennies at hackathon scale. Route 53 is $0.50 a month and
  the ACM certificate is free.


5. CHALLENGES
-------------

Hosting the Fetch.ai agent
- SpacetimeDB refuses to call private or localhost addresses, so the game server couldn't reach the
  agent on a laptop. We exposed it through a Cloudflare tunnel (real hosting is the next step).

Finding an image-to-image AI we could actually use
- ASI:One's image endpoint is text-only: it ignores the input doodle, so it couldn't "upgrade" a
  drawing.
- Gemini's image model has a free quota of 0, and our Google AI Pro subscription doesn't include
  API credits (consumer plan vs developer API billing).
- Amazon Bedrock (Stability's sketch and inpaint models) was the best fit on paper, but our new AWS
  account was blocked pending "corporate customer" verification.
- Solution: xAI Grok Imagine with the MHacks credit. It was tested, integrated and working in a
  live round within the hour, thanks to our provider-agnostic design.

Putting it on a real domain
- A bare domain (doodleffa.tech, no www) can't point at CloudFront with a normal CNAME record. We
  moved DNS to Route 53, whose "alias" records can.
- CloudFront only accepts HTTPS certificates from one AWS region (us-east-1, N. Virginia).
- The site is one page that picks its screen from the URL, but S3 only knows real files, so a
  scanned /play?room=CODE link returned AccessDenied. CloudFront now answers missing paths with
  index.html.

Real-time multiplayer bugs
- The 20 Hz battle tick was silently rejected by SpacetimeDB's scheduler because of an identity
  check. Fixed by comparing against the database's own identity.
- One stale fighter row crashed every room's simulation. We added per-room isolation, cleanup
  between rounds, and a debug event log.
- Reloading the big screen created a new room code and stranded every phone. The screen now
  reclaims its room.
- Players' colors changed after reconnecting. Disconnected players now keep their row.

Fairness and game feel
- Balancing AI-designed weapons: one damage-per-second target for all, plus per-type knockback and
  cooldowns.
- The boomerang was overpowered (it hit on the way out AND back). We shortened both legs, allowed
  only one in the air per player, and shrank its hitbox.
- 20 special abilities interacting with weapons (invisibility, shields, rage, nukes) without
  breaking the damage, knockback and vibration logic.
- Weapons didn't scale when the camera zoomed for bigger arenas, and old weapon art leaked into
  new rounds. Fixed with zoom-aware scaling and content-keyed art caching.

Phones are hard
- Phones zoomed in on double-tap and pinch mid-fight. We disabled zoom and added a
  rotate-to-landscape hint.
- iPhone Safari can't vibrate from a web page, so iPhones get a red damage border instead.
- Audio on phones only plays after a tap, so audio is unlocked on the first interaction.

Teamwork and integration
- Several features were built in parallel on separate branches (special abilities, controller
  audio, damage vibration, menus, weapon art) and merged into one game, resolving
  conflicts in the core simulation each time.
- Testing a 12-player game with a few people: we wrote a load tester (fake controllers) and
  Playwright scripts that play real rounds in a browser.
- Key hygiene: all API keys live in a gitignored .env file and a private server table. We
  scanned for keys before every commit.


6. PRESENTER NOTES (NOT FOR SLIDES)
-----------------------------------
- AI weapon design (ASI:One) is ON (RUN_GENERATION = true). In a live test the AI weapon was
  locked in about 6 s after a last-second submit.
- If a player taps "See my weapon" while the AI is still designing, the server makes the phone
  retry quietly for up to 8 s from the start of Drop (SPEC_WAIT_S in server/src/balance.ts), then
  falls back to the shape-based weapon.
- Weapon art (xAI), weapon sounds (ElevenLabs) and the commentator are ON.
- Weapon design currently goes through the Weapon Smith agent (SPEC_PROVIDER=agent), reached through
  a temporary Cloudflare tunnel. If the tunnel or agent is down, the game falls back to the
  shape-based weapon. To go back to calling ASI:One directly, set SPEC_PROVIDER=asi1 in .env and
  rerun scripts/set-secrets.ts.
- Domain doodleffa.tech is set up: Route 53 DNS, ACM certificate (waiting on validation), private
  S3 bucket and CloudFront distribution with alias records. Still to do: attach the certificate and
  domain names to CloudFront, publish the server to Maincloud (pause the idle 20 Hz tick first),
  then build with VITE_PUBLIC_URL=https://doodleffa.tech and upload to S3.
